Python-Based Data Processing into Snowflake (DAGKit Orchestration)

Production technical depth, code implementation patterns, state management, runtime branching, idempotent loading, observability, and interview defense.

1 · Technical flow summary (One-liner for interviews)

How every architectural layer connects — from Python orchestration to Snowflake and downstream SingleStore.

2 · Production code implementation patterns

How code is structured across jobs, connections, dynamic state, branching, DML, and auditing.

A • Core Framework & Job Definition

Custom Orchestration with DAGKit

Each pipeline is instantiated as a Job object. Individual processing steps are decorated Python functions called nodes. The framework automatically manages connection pooling, variable passing, and contextual dependencies.

# How you define a job and a node
job = Job("SF_RTL_FR_RECAP_SEM_PVT")

@job.node("Set_Variables", "execute")
def f(job_context: JobContext, node_context: NodeContext, exec_context: ExecutionContext):
    # Framework injects JobContext, NodeContext, and ExecutionContext automatically
    ...
Say this in the interview: “We use a custom Python-based orchestration framework called DAGKit. Each pipeline is defined as a Job object, and individual processing steps are decorated Python functions called nodes. The framework manages connections, variable passing between nodes, and execution context — so each node function receives a JobContext, NodeContext, and ExecutionContext as arguments.”
B • Managed Connection & SQL Execution

Executing SQL Against Snowflake

Nodes obtain a cursor from the framework's managed connection. Queries are parameterized and compiled using exec_context.query_builder.prepare(), preventing injection and handling variable interpolation automatically.

cursor = exec_context.connection.cursor()

query = exec_context.query_builder.prepare("""
    SELECT COALESCE(MAX(AS_OF_RPTG_DT), CURRENT_DATE)
    FROM GBI_RETAIL_SEMANTIC_DB.RETAIL.RTL_STR_WKLY_METRIC_AGG_RECAP_PVT;
""")
cursor.execute(query)
rows = cursor.fetchone()
Say this in the interview: “Within each node, we get a cursor from the execution context's managed connection, prepare the query through a query builder — which handles variable interpolation — and then execute it. We don't manage raw connections ourselves; the framework handles pooling and lifecycle.”
C • State Passing & Dynamic Variables

Dynamic Variable Setting & State Passing

The pipeline is parameterized at runtime rather than relying on hardcoded configuration. The initial Set_Variables node queries metadata tables to dynamically determine current reporting periods.

# Setting state in Set_Variables node
exec_context.variable.set("curr_performance_year", str(rows[0]))
exec_context.variable.set("curr_run_ind", "Y")

# Reading downstream via ${variable} interpolation in SQL
query = exec_context.query_builder.prepare("""
    WHERE as_of_rptg_dt = TO_DATE('${curr_date}', 'YYYY-MM-DD')
""")
Say this in the interview: “One of the key patterns is dynamic variable setting. The first node — Set_Variables — queries fiscal calendar metadata and sets runtime variables like current performance year, quarter start/end dates, and run indicators. Downstream nodes read those variables via exec_context.variable.get() or SQL interpolation. This parameterizes the entire pipeline dynamically at runtime.”
D • Runtime DAG Branching

Dynamic DAG Execution Control

Rather than a static DAG where all nodes run unconditionally, the return value of a node is a list of node names to activate next. If there is no work to do, it gracefully routes to a no-op Dummy_Node.

# Return value determines which downstream nodes are activated
if curr_run_ind == 'Y' and (buff_run_ind == 'Y' or snap_run_ind == 'Y'):
    return ["curr_qtr_node", "buffer_and_completed_qtr_node"]
elif curr_run_ind == 'Y':
    return ["curr_qtr_node"]
elif buff_run_ind == 'Y' or snap_run_ind == 'Y':
    return ["buffer_and_completed_qtr_node"]
else:
    return ["Dummy_Node"]  # Graceful exit if no data to process
Say this in the interview: “The Set_Variables node controls which downstream nodes actually execute. Based on the run indicators it sets, the function returns a list of node names to activate. So the DAG is not statically wired — it branches at runtime depending on the data state. The Dummy_Node acts as a graceful no-op exit when there's nothing to process.”
E • Idempotent Loading Pattern

DELETE + INSERT Atomic Transactions

Ensures exact-once idempotency across retries. The target partition is selectively cleared, refreshed data is inserted, and transactions are committed explicitly.

# Step 1: Clear the target partition
query = exec_context.query_builder.prepare("""
    DELETE FROM GBI_RETAIL_SEMANTIC_DB.RETAIL_APP.RTL_STR_METRIC_RATING_CURR_QTR_PVT
    WHERE performance_year = '${curr_performance_year}' 
      AND performance_qtr = '${curr_performance_qtr}';
""")
cursor.execute(query)
logging.info("Rows affected: {}".format(cursor.rowcount))

# Step 2: Insert computed results
query = exec_context.query_builder.prepare("""
    INSERT INTO GBI_RETAIL_SEMANTIC_DB.RETAIL_APP.RTL_STR_METRIC_RATING_CURR_QTR_PVT
    SELECT ... FROM ... WHERE ...;
""")
cursor.execute(query)
logging.info("Rows affected: {}".format(cursor.rowcount))

# Step 3: Explicit commit
exec_context.connection.commit()
Say this in the interview: “The actual data loading is done through DELETE + INSERT patterns within nodes — we selectively delete the target partition first, then re-insert computed results. We log cursor.rowcount after every DML statement for observability, and we commit explicitly at the end of each node.”
F • Observability & Auditing

Logging Session IDs, Rowcounts & Snowflake Query IDs

Every node provides transparent runtime tracking by querying metadata and Snowflake session history tables.

# Capture Session ID
logging.info("---SESSION ID--- {}".format(rows[0]))

# Capture rows affected after every DML
logging.info("Rows affected: {}".format(cursor.rowcount))

# Query Snowflake information schema to capture Query ID
query = exec_context.query_builder.prepare("""
    SELECT query_id 
    FROM table(information_schema.query_history_by_session())
    ORDER BY start_time DESC LIMIT 1;
""")
cursor.execute(query)
logging.info("---QUERY ID--- {}".format(cursor.fetchone()[0]))
Say this in the interview: “Every node logs the session ID at the start, the row count after every DML, and we query Snowflake's information_schema.query_history_by_session to capture the actual Snowflake query ID for post-run auditing and debugging.”

3 · Likely follow-up questions & your answers

Three core architectural questions interviewers ask about this pipeline, with exact high-scoring answers.

Pipeline Resiliency & Failure Recovery

“How do you handle failures mid-pipeline?”

“The job config defines a restartPolicy: standard and retryCount. If a node fails, the framework can restart from the failed node rather than re-running the entire job. We also have maxSLA defined — if the job exceeds that window, it alerts.”
Data Integrity & Partition Management

“How do you ensure idempotency?”

“The DELETE + INSERT pattern ensures we can re-run safely — we always clear the target partition before writing, keyed on Performance_year and Performance_qtr, so there's no risk of duplicates on a retry.”
CI/CD & Release Engineering

“How do you test before promoting to production?”

“We have separate Darwin environments — E19 for DEV, E21 for TEST, E27 for PROD — each with their own SLA and priority configurations. The job is promoted through these environments with the same code but different connection targets.”
